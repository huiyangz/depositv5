# ST005 检查账户是否存在限制

## 目标与范围

本 Spec 规范存款交易执行步骤 ST005「检查账户是否存在限制」的行为：以输入账号查询【账户信息】取得主账户标志与上级账户内部键并判定子账户；子账户时按上级账户内部键取得主账户账号；设置待查账户（子账户取主账户账号，否则取输入账号）；按待查账户查询限制状态为 "A-生效" 的【账户限制信息】；将账号、主账户标志与每条生效限制的限制编号、账户限制类型、限制状态赋值到步骤输出返回。

范围：步骤内对【账户信息】与【账户限制信息表】的只读查询、子账户判定与待查账户设置、输出赋值、失败语义。

不在范围：leadAcctFlag 子账户/非子账户具体取值的确定（见「验收范围」第 1 条）；输入账号有效性的上游校验；限制记录的建立、维护与解除；限制类型业务含义的判断；下游步骤对本步骤输出的使用。

## 正式需求来源

- docs/requirements/ST005.md（任务编号 ST005，版本 1）：「步骤描述」第 1–4 条、「输入」、「输出」、「相关枚举」、「补充说明」、「失败处理」、「已接受的需求处理结论」。

术语与实体绑定（结合工程确认的技术约束）：

- 【账户信息】= 对公存款账户主表（RB_BUS_ACCT），数据服务接口 `IRbBusAcctBcc`。涉及字段：BASE_ACCT_NO（账号）、LEAD_ACCT_FLAG（主账户标志，String，无枚举绑定）、PARENT_INTERNAL_KEY（上级账户内部键）、INTERNAL_KEY（账户内部键值，主键）。
- 【账户限制信息表】= 对公存款账户限制表（RB_BUS_RESTRAINTS），数据服务接口 `IRbBusRestraintsBcc`。涉及字段：BASE_ACCT_NO（账号）、RESTRAINTS_STATUS（限制状态）、RES_SEQ_NO（限制编号）、RESTRAINT_TYPE（账户限制类型）。
  绑定依据（需求「已接受的需求处理结论」第 2 条，已放行）：需求输出表来源实体列标注客户限制表（RB_CLIENT_RESTRAINTS），但该表无账号字段，无法按账号查询；与步骤 3 按账号的查询条件及 resSeqNo、restraintType、restraintsStatus 三个输出字段一一对应的是 RB_BUS_RESTRAINTS。本 Spec 按可执行的实体绑定（RB_BUS_RESTRAINTS），该差异如实记录，不改动需求原文，后续生成与审核不再以此阻断。
- 步骤契约：输出 BO 继承 `StepResult`（succeed / errorCode / errorMessage），步骤接口形态 `execute(InputBO): OutputBO`，与既有交易执行步骤一致。

## 输入、输出及依赖契约

输入（ST005InputBO）：

| 字段名 | 类型 | 必填性 | 说明 |
|--------|------|--------|------|
| baseAcctNo | java.lang.String | 必填 | 账号；必填性由上游交易输入保证，本步骤不定义空值校验分支 |

输出（ST005OutputBO extends StepResult）：

| 字段名 | 元素类型 | 标记 | 来源 | 空值 / 集合语义 |
|--------|----------|------|------|-----------------|
| baseAcctNo | java.lang.String | 非必填 | 【账户信息】按输入账号查询所得记录 | 记录字段值原样输出（见 REQ-001，即使子账户也不改取主账户记录值） |
| leadAcctFlag | java.lang.String | 非必填 | 同上（同一次查询所得记录） | 记录字段值原样输出，记录字段为空则输出为空 |
| resSeqNo | java.lang.String | 集合 | 【账户限制信息表】待查账户的生效限制记录 | 每条生效限制一个元素；未查得生效限制时为不含任何元素的空集合 |
| restraintType | com.dcits.depsit.enums.RestraintType | 集合 | 同上 | 同上 |
| restraintsStatus | com.dcits.depsit.enums.RestraintsStatus | 集合 | 同上 | 同上；因查询条件限定状态为 "A-生效"，每个元素值均为 RestraintsStatus.A |

- 元素对应关系：三个集合同一下标的元素来自同一条生效限制记录。
- 顺序：需求未规定集合元素顺序，本 Spec 不约束顺序，实现与测试断言不得依赖顺序。
- 枚举：RestraintsStatus：A=已批准（需求表述 "A-生效"，以取值 "A" 为准）、E=已终止、F=未生效。RestraintType 为代码类枚举（"4"…"96"、"DX1"、"DX2"、"EMR"、"SF1"、"SF2"、"SK1"、"YC1"、"YC2" 等），取值以代码为准，本步骤不按限制类型筛选。
- 步骤内部中间数据（非输出）：$主账户标志$、$上级账户内部键$、$主账户账号$、[待查账户]、[账户限制信息]。

依赖调用（除以下查询外，本步骤无其他数据访问，无写操作、无状态变更、无外部服务调用）：

1. `IRbBusAcctBcc` 按输入账号查询【账户信息】，一次；
2. 仅子账户情形：`IRbBusAcctBcc` 按上级账户内部键查询【账户信息】，一次；
3. `IRbBusRestraintsBcc` 按待查账户 + 限制状态 "A-生效" 查询【账户限制信息表】，一次。

场景中的账号、内部键、限制编号均为示例数据（满足字段类型与长度约束）；规范常量仅有：限制状态 "A-生效" = RestraintsStatus.A（取值 "A"）。

## Requirements

### Requirement: REQ-001 按输入账号查询账户信息并判定子账户
来源：docs/requirements/ST005.md「步骤描述」第 1 条；「已接受的需求处理结论」第 1 条
系统 SHALL 以输入 {账号}（baseAcctNo）为条件查询【账户信息】，取得该记录的 $主账户标志$（leadAcctFlag）与 $上级账户内部键$（parentInternalKey）；输出 [账号]（baseAcctNo）与 [主账户标志]（leadAcctFlag）SHALL 取自本次查询所得记录的字段值（判定为子账户时也不改取主账户记录的值）。当 $主账户标志$ 表明该账户为子账户时，系统 SHALL 以 $上级账户内部键$ 为条件查询【账户信息】，取匹配记录的账号作为 $主账户账号$；当 $主账户标志$ 未表明为子账户时，系统 MUST NOT 执行按上级账户内部键的查询，直接继续执行。
注：leadAcctFlag 中表示子账户（及非子账户）的具体取值需求未声明，已按「已接受的需求处理结论」第 1 条放行、待业务确认；本条款以"主账户标志表明为子账户"的业务语义表达分支条件，不规定具体取值。

#### Scenario: REQ-001-S01 非子账户仅查询一次账户信息
- **GIVEN** 【账户信息】中存在账号为 "MAIN200010001"（示例）的记录，其主账户标志取值未表明该账户为子账户，上级账户内部键为 90001（示例）
- **WHEN** 以 baseAcctNo = "MAIN200010001" 执行本步骤
- **THEN** 仅发生一次按账号 "MAIN200010001" 查询【账户信息】的调用，不发生按上级账户内部键查询【账户信息】的调用；输出 baseAcctNo = "MAIN200010001"，输出 leadAcctFlag 为该记录的主账户标志字段值

#### Scenario: REQ-001-S02 子账户按上级账户内部键取得主账户账号
- **GIVEN** 【账户信息】中存在账号为 "SUB200010002"（示例）的记录，其主账户标志取值表明该账户为子账户，上级账户内部键为 90001；且存在账户内部键值为 90001、账号为 "MAIN200010001" 的记录
- **WHEN** 以 baseAcctNo = "SUB200010002" 执行本步骤
- **THEN** 先按账号 "SUB200010002" 查询【账户信息】，再按上级账户内部键 90001 查询【账户信息】，$主账户账号$ = "MAIN200010001"；输出 baseAcctNo = "SUB200010002"、输出 leadAcctFlag 为账号 "SUB200010002" 记录的主账户标志字段值（均不取主账户记录的值）

### Requirement: REQ-002 设置待查账户
来源：docs/requirements/ST005.md「步骤描述」第 2 条；「已接受的需求处理结论」第 1 条（子账户判定沿用步骤 1 同一判定）
系统 SHALL 按与 REQ-001 相同的子账户判定设置 [待查账户]：输入 {账号} 为子账户时，[待查账户] = REQ-001 取得的 $主账户账号$；否则 [待查账户] = 输入 {账号}。

#### Scenario: REQ-002-S01 子账户待查账户为主账户账号
- **GIVEN** 输入账号 "SUB200010002" 判定为子账户，REQ-001 取得 $主账户账号$ = "MAIN200010001"
- **WHEN** 设置 [待查账户]
- **THEN** [待查账户] = "MAIN200010001"，步骤 3 的限制查询以该账号为条件

#### Scenario: REQ-002-S02 非子账户待查账户为输入账号
- **GIVEN** 输入账号 "MAIN200010001" 未判定为子账户
- **WHEN** 设置 [待查账户]
- **THEN** [待查账户] = "MAIN200010001"

### Requirement: REQ-003 按待查账户查询生效账户限制信息
来源：docs/requirements/ST005.md「步骤描述」第 3 条；「已接受的需求处理结论」第 2 条（实体绑定）
系统 SHALL 以 [待查账户] 与 $限制状态$ = "A-生效"（RestraintsStatus.A）为条件查询【账户限制信息表】（对公存款账户限制表 RB_BUS_RESTRAINTS）一次，取得全部匹配的 [账户限制信息] 记录，每条记录 MUST 含 $账户限制类型$（restraintType）与 $限制编号$（resSeqNo）。未查得匹配记录不构成失败。

#### Scenario: REQ-003-S01 查得多条生效限制
- **GIVEN** 【账户限制信息表】中待查账户 "MAIN200010001" 存在 3 条限制状态为 "A-生效" 的记录，限制编号分别为 R0001、R0002、R0003（示例），账户限制类型互不相同
- **WHEN** 按 [待查账户] = "MAIN200010001" 查询生效限制
- **THEN** 查得且仅查得这 3 条记录，每条记录含其限制编号与账户限制类型

#### Scenario: REQ-003-S02 仅生效状态记录被查得
- **GIVEN** 待查账户 "MAIN200010001" 存在 2 条限制状态 "A-生效"、1 条 "E-已终止"、1 条 "F-未生效" 的记录
- **WHEN** 查询生效限制
- **THEN** 仅查得 2 条 "A-生效" 记录，"E"、"F" 状态记录不进入结果

#### Scenario: REQ-003-S03 待查账户无任何限制记录
- **GIVEN** 待查账户 "MAIN200010001" 在【账户限制信息表】中无任何记录
- **WHEN** 查询生效限制
- **THEN** 查得记录数为 0，该情形不构成失败

### Requirement: REQ-004 赋值并返回账户限制信息输出
来源：docs/requirements/ST005.md「步骤描述」第 4 条；「输出」表 resSeqNo / restraintType / restraintsStatus 三行
系统 SHALL 将 [账户限制信息] 赋值到输出并返回：resSeqNo、restraintType、restraintsStatus 三个集合 MUST 每条生效限制一个元素；同一下标的三个集合元素 MUST 来自同一条生效限制记录；restraintsStatus 每个元素值均为 "A-生效"（RestraintsStatus.A）。未查得生效限制时三个集合均为不含任何元素的空集合。集合元素顺序需求未规定，实现与断言不得依赖顺序。

#### Scenario: REQ-004-S01 每条生效限制对应一组输出元素
- **GIVEN** REQ-003 查得待查账户 "MAIN200010001" 的 3 条生效限制记录：R0001/类型 "13"、R0002/类型 "56"、R0003/类型 "DX2"（均为示例值，"13"、"56"、"DX2" 是 RestraintType 枚举既有取值）
- **WHEN** 赋值输出
- **THEN** resSeqNo 含且仅含 "R0001"、"R0002"、"R0003" 三个元素；restraintType 含且仅含对应 "13"、"56"、"DX2" 的 RestraintType 枚举值三个元素；restraintsStatus 含且仅含 3 个元素且均为 RestraintsStatus.A；任一下标 i 处三个集合的元素均来自同一记录

#### Scenario: REQ-004-S02 未查得生效限制时输出空集合
- **GIVEN** REQ-003 查得待查账户 "MAIN200010001" 的生效限制记录数为 0
- **WHEN** 赋值输出
- **THEN** resSeqNo、restraintType、restraintsStatus 均为不含任何元素的空集合；[账号]、[主账户标志] 仍按 REQ-001 正常输出

### Requirement: REQ-005 无业务失败与技术异常传播
来源：docs/requirements/ST005.md「失败处理」
本步骤 SHALL 无业务失败场景：全部业务情形（含未查得任何生效限制）均成功结束，succeed = true，不设置 errorCode 与 errorMessage。失败仅由技术异常表达：任一依赖查询发生技术异常时，系统 MUST 不捕获、不转换、不吞并，按原样向调用方传播，且不产生步骤输出。

#### Scenario: REQ-005-S01 全部业务情形成功结束
- **GIVEN** 任一业务情形执行完成（含 REQ-003-S03 未查得记录、REQ-004-S02 输出空集合）
- **WHEN** 步骤执行完成返回
- **THEN** 输出 succeed = true，errorCode 与 errorMessage 为空（null）

#### Scenario: REQ-005-S02 技术异常原样传播
- **GIVEN** 按输入账号查询【账户信息】的调用抛出技术异常（如数据访问异常）
- **WHEN** 执行本步骤
- **THEN** 该异常按原样向调用方传播，不被捕获、转换或吞并，不返回带业务错误码的步骤输出

## 验收范围与明确不覆盖的事项

覆盖：按输入账号查询【账户信息】及输出的来源绑定；子账户/非子账户两条路径（含第二次账户信息查询的执行与禁止）；待查账户设置；按待查账户 + "A-生效" 的限制查询（多条、仅生效、无记录三种查询结果）；三个集合输出的元素对应与空集合语义；无业务失败与技术异常传播。

明确不覆盖：

1. leadAcctFlag 表示子账户（及非子账户）的具体取值：需求未声明，已按「已接受的需求处理结论」第 1 条放行、待业务确认；两条路径的行为已按业务语义规定，场景以"主账户标志取值表明/未表明为子账户"表述，不使用具体字面值。
2. 输入 baseAcctNo 为空的校验分支：必填由上游交易输入保证。
3. 输入账号在【账户信息】无匹配记录、子账户的上级账户内部键在【账户信息】无匹配记录的情形：需求未定义其处理，本 Spec 不规定。
4. 集合元素的排序：需求未规定，不约束。
5. 限制记录的建立、维护、解除及限制类型业务含义判断：属其他任务。
6. 输出表来源实体差异：需求将 resSeqNo/restraintType/restraintsStatus 的来源实体标注为客户限制表（RB_CLIENT_RESTRAINTS），本 Spec 依据已接受结论 2 绑定对公存款账户限制表（RB_BUS_RESTRAINTS），差异已在「正式需求来源」记录。
