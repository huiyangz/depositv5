# ST102 登记累计限额

## 目标与范围

本任务为交易执行步骤：当[限额检查结果]为"未超限"，且（[限额累计金额]等于 0 或[限额累计笔数]等于 0）时，向【限额累计信息表】（RB_LIMIT_SUM_INFO）登记（新增）一条限额累计记录：$限额场景编码$取输入[限额场景编码]；$限额检查对象值$依据按[限额场景编码]查询【限额场景定义】（RbLimitSceneDef）取得的$限额检查对象类型$赋值为{账号}或{客户号}；$限额累计金额$取{交易金额}；$限额累计笔数$为 1；$生效日期$取{核心运行日期}；$失效日期$为{核心运行日期}加上按[限额场景编码]查询【限额控制配置】（RbLimitCtrlConf）取得的$周期类型$与$周期值$所确定的周期；其余字段按系统规则自动生成。登记结果六个字段作为步骤输出返回。条件不满足时不登记，步骤正常返回且输出为空。

- 范围内：登记条件的判定（含"等于 0"判定口径与布尔组合）、限额检查对象值按检查对象类型的取值映射、登记字段的显式赋值与写入【限额累计信息表】、失效日期按控制配置周期的加法、输出的取值与空值语义、技术异常向上传播。
- 不在范围内：已有累计记录的更新与删除维护；限额检查判定本身（检查限额组件职责）；输入必填性校验；"其他字段"自动生成的具体规则；登记结果在后续交易流程中的使用。

## 输入、输出及依赖契约

### 输入

| 字段名 | 类型 | 必填性 | 说明 |
|--------|------|--------|------|
| limitCheckResult | java.lang.String | 必填 | 限额检查结果；与需求正文常量"未超限"做 String 等值比较 |
| baseAcctNo | java.lang.String | 必填 | 账号；$限额检查对象类型$为"账户级别（ACCT）"时作为 $限额检查对象值$ |
| clientNo | java.lang.String | 必填 | 客户号；$限额检查对象类型$为"客户级别（CUST）"时作为 $限额检查对象值$ |
| tranAmt | java.math.BigDecimal | 必填 | 交易金额；登记时 $限额累计金额$ 取该值（原样赋值，不计算、不舍入） |
| limitSceneNo | java.lang.String | 必填 | 限额场景编码；查询【限额场景定义】【限额控制配置】的键，同时是登记的 $限额场景编码$ |
| runDate | java.util.Date | 必填 | 核心运行日期（来源实体：系统日期表 FM_DATE）；$生效日期$ 取该值，$失效日期$ 以该值为基准加周期 |
| limitSumAmt | java.math.BigDecimal | 必填 | 限额累计金额（登记前累计值），仅用于登记条件判定 |
| limitSumCnt | java.lang.Integer | 必填 | 限额累计笔数（登记前累计值），仅用于登记条件判定 |
| reference | java.lang.String | 必填 | 交易参考号；需求正文未将其绑定到登记字段的显式赋值（记录其余字段按系统规则自动生成） |

判定口径：[限额累计金额]等于 0 按数值上等于 0 判断（BigDecimal 的 0 与 0.00 均视为等于 0）；[限额累计笔数]等于 0 按 Integer 等于 0 判断。

需求未定义必填输入缺失或为空（null）时的处理（「失败处理」声明无业务失败场景），必填性由上送方保证，本 Spec 不发明校验或报错行为。

### 输出

| 字段名 | 类型 | 必填性 | 来源实体 | 说明 |
|--------|------|--------|----------|------|
| limitSceneNo | java.lang.String | 非必填 | 限额累计信息表（RB_LIMIT_SUM_INFO） | 限额场景编码，登记时等于输入[限额场景编码] |
| checkObjVal | java.lang.String | 非必填 | 限额累计信息表（RB_LIMIT_SUM_INFO） | 限额检查对象值，登记时按检查对象类型取{账号}或{客户号} |
| limitSumAmt | java.math.BigDecimal | 非必填 | 限额累计信息表（RB_LIMIT_SUM_INFO） | 限额累计金额，登记时等于{交易金额} |
| limitSumCnt | java.lang.Integer | 非必填 | 限额累计信息表（RB_LIMIT_SUM_INFO） | 限额累计笔数，登记时恒为 1 |
| effectDate | java.util.Date | 非必填 | 限额累计信息表（RB_LIMIT_SUM_INFO） | 生效日期，登记时等于{核心运行日期} |
| expireDate | java.util.Date | 非必填 | 限额累计信息表（RB_LIMIT_SUM_INFO） | 失效日期，登记时等于{核心运行日期}＋控制周期（见 REQ-004） |

空值语义：六个输出字段均非必填。发生登记时，六字段回显本次登记写入记录的对应取值；登记条件不满足、未发生登记时，步骤正常返回且六字段均为 null，不填充默认值（依据：「输出」全部字段标记非必填，「失败处理」声明无业务失败场景）。

字段名说明：输出 limitSumCnt（限额累计笔数）对应 RB_LIMIT_SUM_INFO 的累计笔数列，该列在库表 DDL 与实体类中名为 `否`（INT，可空），为既有契约，本 Spec 按需求「输出」表字段名表达，不改名。

### 数据访问与依赖（技术约束）

| 需求实体 | 工程对象 / 数据服务 | 表与访问约束 |
|----------|--------------------|--------------|
| 限额场景定义（RbLimitSceneDef） | RbLimitSceneDefEO / IRbLimitSceneDefBcc | RB_LIMIT_SCENE_DEF，主键 LIMIT_SCENE_NO；以输入[限额场景编码]按主键等值查询，至多一条；读取 CHECK_OBJ_TYPE（VARCHAR(10)，可空，枚举 CheckObjType） |
| 限额控制配置（RbLimitCtrlConf） | RbLimitCtrlConfEO / IRbLimitCtrlConfBcc | RB_LIMIT_CTRL_CONF，主键 (LIMIT_BRANCH_ID, LIMIT_SCENE_NO)；需求仅以[限额场景编码]等值查询，读取 PERIOD_TYPE（VARCHAR(1)，枚举 TermType）与 PERIOD_VALUE（VARCHAR(5)） |
| 限额累计信息表 | RbLimitSumInfoEO / IRbLimitSumInfoBcc | RB_LIMIT_SUM_INFO，主键 (CHECK_OBJ_VAL, LIMIT_SCENE_NO)；本步骤新增一条记录（登记），不更新、不删除已有记录 |

- RB_LIMIT_CTRL_CONF 主键含 LIMIT_BRANCH_ID，需求未给出该查询条件，亦未定义同场景编码多条配置并存时的选取规则；验收场景以"[限额场景编码]等值查询能够取得周期类型与周期值"为前提，多条命中时的选取不纳入验收。
- 检查对象类型枚举 CheckObjType 现有常量：ACCT（账户级别）、CARD（卡片级别）、CDGROUP（卡组）、CUST（客户级别）。需求正文仅定义赋值为{账号}或{客户号}两种取值情形；对象类型为 CARD、CDGROUP 时 $限额检查对象值$ 的取值需求未写明，且已按「已接受的需求处理结论」豁免，本 Spec 不为其发明取值，亦不纳入验收断言。
- 期限类型枚举 TermType 常量与周期单位（技术约束，来自枚举定义）：D→日；W→周（7 日）；M→月；Q→季（3 月）；H→半年（6 月）；Y→年。$失效日期$ = {核心运行日期} ＋ $周期值$ × 周期单位，按日历日期计算；月末/季末等日历边界的取整规则需求未定义，不在断言范围。
- 登记记录中未被正文显式赋值的其他字段——限额累计描述（LIMIT_SUM_CONTENT）、客户号（CLIENT_NO）、原交易参考号（PRE_REFERENCE）、交易币种（TRAN_CCY）、交易参考号（REFERENCE）、创建时间戳（CREATE_TIMESTAMP）、最后修改时间戳（LAST_UPD_TIMESTAMP）——"按照系统规则自动生成"：需求未定义其具体生成规则，不在验收断言范围；其中 CLIENT_NO、REFERENCE、CREATE_TIMESTAMP、LAST_UPD_TIMESTAMP 为 NOT NULL 列，取值由系统规则保证写入成功。
- 日期口径：核心运行日期、生效日期、失效日期按日期（年月日）口径表达与断言；EFFECT_DATE、EXPIRE_DATE 列类型为 TIMESTAMP(3)，其时间部分需求未定义口径，不在断言范围。
- 本步骤为写入步骤：登记仅新增一条记录；存量数据主键 (CHECK_OBJ_VAL, LIMIT_SCENE_NO) 重复导致的新增失败属技术异常，按技术异常传播表达。

## Requirements

### Requirement: REQ-001 登记条件判定

来源：`docs/requirements/ST102.md`「步骤描述」步骤1（条件部分："若[限额检查结果]为'未超限'，且（[限额累计金额]等于0或者[限额累计笔数]等于0）"）
当且仅当[限额检查结果]（limitCheckResult）为"未超限"（String 等值），且[限额累计金额]（limitSumAmt）数值上等于 0 或[限额累计笔数]（limitSumCnt）等于 0（两者满足其一）时，系统 SHALL 执行登记（按 REQ-002～REQ-004）；条件任一不满足时，系统 SHALL NOT 向【限额累计信息表】（RB_LIMIT_SUM_INFO）写入任何记录（无新增、无更新、无删除），步骤 SHALL 正常返回且六个输出字段均为 null。

#### Scenario: REQ-001-S01 未超限且累计金额等于0→登记

- **GIVEN** 输入 limitCheckResult="未超限"、limitSumAmt=0.00（数值上等于 0，小数位不影响判定）、limitSumCnt=2（示例值）
- **WHEN** 执行 ST102 步骤
- **THEN** 登记条件满足，按 REQ-002～REQ-004 登记限额信息

#### Scenario: REQ-001-S02 未超限且累计笔数等于0→登记

- **GIVEN** 输入 limitCheckResult="未超限"、limitSumAmt=15000.00、limitSumCnt=0（示例值）
- **WHEN** 执行 ST102 步骤
- **THEN** 登记条件满足，按 REQ-002～REQ-004 登记限额信息

#### Scenario: REQ-001-S03 未超限且累计金额与笔数均为0→登记

- **GIVEN** 输入 limitCheckResult="未超限"、limitSumAmt=0、limitSumCnt=0
- **WHEN** 执行 ST102 步骤
- **THEN** 登记条件满足，按 REQ-002～REQ-004 登记限额信息

#### Scenario: REQ-001-S04 未超限但累计金额与笔数均大于0→不登记

- **GIVEN** 输入 limitCheckResult="未超限"、limitSumAmt=15000.00、limitSumCnt=3（两者均不等于 0，示例值）
- **WHEN** 执行 ST102 步骤
- **THEN** 登记条件不满足：RB_LIMIT_SUM_INFO 不新增、不更新、不删除任何记录；步骤正常返回（无业务失败），输出 limitSceneNo、checkObjVal、limitSumAmt、limitSumCnt、effectDate、expireDate 均为 null

#### Scenario: REQ-001-S05 限额检查结果非"未超限"→不登记

- **GIVEN** 输入 limitCheckResult="超限"（示例值，任一非"未超限"取值同理）、limitSumAmt=0、limitSumCnt=0
- **WHEN** 执行 ST102 步骤
- **THEN** 登记条件不满足：同 REQ-001-S04，不写入任何记录，正常返回，六个输出字段均为 null

### Requirement: REQ-002 限额检查对象值按检查对象类型取值

来源：`docs/requirements/ST102.md`「步骤描述」步骤1（"$限额检查对象值$根据{限额场景编码}查询限额场景定义（RbLimitSceneDef）取得的$限额检查对象类型$赋值为{账号}或者{客户号}"）
登记时，系统 SHALL 以输入[限额场景编码]（limitSceneNo）查询【限额场景定义】（RB_LIMIT_SCENE_DEF，主键等值查询，至多一条）取得$限额检查对象类型$（checkObjType），并按其取值赋$限额检查对象值$（checkObjVal）：为"账户级别（ACCT）"时 SHALL 等于输入{账号}（baseAcctNo）；为"客户级别（CUST）"时 SHALL 等于输入{客户号}（clientNo）。对象类型为 CARD、CDGROUP 时的取值需求未写明（见「已接受的需求处理结论」），本条款不为其定义行为。

#### Scenario: REQ-002-S01 检查对象类型为账户级别→取账号

- **GIVEN** RB_LIMIT_SCENE_DEF 存在 LIMIT_SCENE_NO="DEP0001" 的记录，CHECK_OBJ_TYPE="ACCT"（示例数据）；输入 baseAcctNo="1002003004005006"、clientNo="C0001"、limitSceneNo="DEP0001"，登记条件满足
- **WHEN** 执行登记
- **THEN** 登记记录的 $限额检查对象值$（CHECK_OBJ_VAL）为 "1002003004005006"（{账号}），输出 checkObjVal="1002003004005006"

#### Scenario: REQ-002-S02 检查对象类型为客户级别→取客户号

- **GIVEN** RB_LIMIT_SCENE_DEF 存在 LIMIT_SCENE_NO="DEP0001" 的记录，CHECK_OBJ_TYPE="CUST"（示例数据）；输入同 REQ-002-S01，登记条件满足
- **WHEN** 执行登记
- **THEN** 登记记录的 $限额检查对象值$（CHECK_OBJ_VAL）为 "C0001"（{客户号}），输出 checkObjVal="C0001"

### Requirement: REQ-003 登记限额信息的字段赋值与写入

来源：`docs/requirements/ST102.md`「步骤描述」步骤1（"$限额场景编码$等于[限额场景编码]……$限额累计金额$等于{交易金额}，$限额累计笔数$等于1，$生效日期$等于{核心运行日期}……其他字段的取值按照系统规则自动生成"）、「输出」表
登记时，系统 SHALL 向【限额累计信息表】（RB_LIMIT_SUM_INFO）新增一条记录，显式赋值为：$限额场景编码$（LIMIT_SCENE_NO）＝输入[限额场景编码]；$限额累计金额$（LIMIT_SUM_AMT）＝输入{交易金额}（tranAmt，原样赋值，不计算、不舍入）；$限额累计笔数$（`否` 列）＝1；$生效日期$（EFFECT_DATE）＝输入{核心运行日期}（runDate）；$限额检查对象值$（CHECK_OBJ_VAL）按 REQ-002；$失效日期$（EXPIRE_DATE）按 REQ-004。其余字段的取值 SHALL 按系统规则自动生成（需求未约束具体规则，不作断言）。步骤输出 SHALL 回显登记值：limitSceneNo、checkObjVal、limitSumAmt、limitSumCnt、effectDate、expireDate 分别等于上述登记取值。

#### Scenario: REQ-003-S01 登记一条限额累计记录并回显输出

- **GIVEN** 登记条件满足（REQ-001-S01 情形）；RB_LIMIT_SCENE_DEF 中 LIMIT_SCENE_NO="DEP0001" 的记录 CHECK_OBJ_TYPE="ACCT"；RB_LIMIT_CTRL_CONF 中 LIMIT_SCENE_NO="DEP0001" 的记录 PERIOD_TYPE="M"、PERIOD_VALUE="1"；输入 baseAcctNo="1002003004005006"、clientNo="C0001"、tranAmt=1000.00、limitSceneNo="DEP0001"、runDate=2026-06-15（示例数据）
- **WHEN** 执行登记
- **THEN** RB_LIMIT_SUM_INFO 新增一条记录（不更新、不删除其他记录）：LIMIT_SCENE_NO="DEP0001"、CHECK_OBJ_VAL="1002003004005006"、LIMIT_SUM_AMT=1000.00（BigDecimal 原样）、`否`=1、EFFECT_DATE=2026-06-15、EXPIRE_DATE 按 REQ-004（本例为 2026-07-15）；输出 limitSceneNo="DEP0001"、checkObjVal="1002003004005006"、limitSumAmt=1000.00、limitSumCnt=1、effectDate=2026-06-15、expireDate=2026-07-15

### Requirement: REQ-004 失效日期按限额控制配置周期计算

来源：`docs/requirements/ST102.md`「步骤描述」步骤1（"$失效日期$等于{核心运行日期}加{限额场景编码}查询限额控制配置（RbLimitCtrlConf）取得的$周期类型$$周期值$"）
登记时，系统 SHALL 以输入[限额场景编码]（limitSceneNo）等值查询【限额控制配置】（RB_LIMIT_CTRL_CONF）取得$周期类型$（periodType）与$周期值$（periodValue），并 SHALL 将 $失效日期$（expireDate）计算为 {核心运行日期}（runDate）加 $周期值$ 个周期单位；周期单位由 $周期类型$ 决定（TermType 枚举定义）：D→日、W→周（7 日）、M→月、Q→季（3 月）、H→半年（6 月）、Y→年，按日历日期计算；登记记录的 EXPIRE_DATE 与输出 expireDate 均取该计算结果。

以下场景均在登记条件满足、runDate=2026-06-15（示例值，避开日历边界）、[限额场景编码]对应配置存在且周期字段有效的前提下给出。

#### Scenario: REQ-004-S01 周期类型为日、周期值1

- **GIVEN** RB_LIMIT_CTRL_CONF 中 LIMIT_SCENE_NO="DEP0001" 的记录 PERIOD_TYPE="D"、PERIOD_VALUE="1"；输入 runDate=2026-06-15、limitSceneNo="DEP0001"
- **WHEN** 执行登记
- **THEN** 登记记录 EXPIRE_DATE 与输出 expireDate 均为 2026-06-16（2026-06-15 加 1 日）

#### Scenario: REQ-004-S02 周期类型为周、周期值1

- **GIVEN** RB_LIMIT_CTRL_CONF 中 LIMIT_SCENE_NO="DEP0001" 的记录 PERIOD_TYPE="W"、PERIOD_VALUE="1"；输入 runDate=2026-06-15、limitSceneNo="DEP0001"
- **WHEN** 执行登记
- **THEN** 登记记录 EXPIRE_DATE 与输出 expireDate 均为 2026-06-22（2026-06-15 加 1 周＝7 日）

#### Scenario: REQ-004-S03 周期类型为月、周期值1

- **GIVEN** RB_LIMIT_CTRL_CONF 中 LIMIT_SCENE_NO="DEP0001" 的记录 PERIOD_TYPE="M"、PERIOD_VALUE="1"；输入 runDate=2026-06-15、limitSceneNo="DEP0001"
- **WHEN** 执行登记
- **THEN** 登记记录 EXPIRE_DATE 与输出 expireDate 均为 2026-07-15（2026-06-15 加 1 个月）

#### Scenario: REQ-004-S04 周期类型为季、周期值1

- **GIVEN** RB_LIMIT_CTRL_CONF 中 LIMIT_SCENE_NO="DEP0001" 的记录 PERIOD_TYPE="Q"、PERIOD_VALUE="1"；输入 runDate=2026-06-15、limitSceneNo="DEP0001"
- **WHEN** 执行登记
- **THEN** 登记记录 EXPIRE_DATE 与输出 expireDate 均为 2026-09-15（2026-06-15 加 1 季＝3 个月）

## 验收范围与明确不覆盖的事项

### 验收范围

- 5 条需求、16 个验收场景，覆盖：登记条件判定的正常路径与两条否定分支（金额与笔数均大于 0、检查结果非"未超限"，均断言无写入且输出为 null）；检查对象值 ACCT/CUST 两种取值映射；登记写入的全字段断言（含新增一条、不更新不删除的副作用约束）与输出回显；失效日期六种期限类型各一例及周期值大于 1 一例；技术异常传播。
- 每个场景的 THEN 明确写入断言（记录字段值、新增条数、禁止的副作用）或输出断言（六字段取值或 null），可直接推导测试断言；场景中表内数据与输入值均为示例数据，规范常量（"未超限"、笔数 1、TermType/CheckObjType 枚举取值）已单独标明。

### 明确不覆盖

- 必填输入（含 limitCheckResult、reference 等 9 个字段）缺失、为空或 null 时的校验行为：需求仅标记必填，未定义缺失时的处理，必填性由上送方保证。
- $限额检查对象类型$为 CARD、CDGROUP（或按[限额场景编码]查询定义表无记录、类型为空）时 $限额检查对象值$ 的取值：需求未写明，已按「已接受的需求处理结论」豁免，处理记录不等同于补充业务取值，不纳入验收断言。
- 查询【限额控制配置】无记录、或 $周期类型$/$周期值$ 为空时的处理：需求未定义，验收场景以配置存在且周期字段有效为前提；同场景编码多机构配置（主键含 LIMIT_BRANCH_ID）多条命中时的选取规则需求未定义，不纳入验收。
- 月末/季末等日历边界上加月、加季、加半年、加年的取整规则：需求未定义，示例日期均避开边界；EFFECT_DATE/EXPIRE_DATE 的时间部分（TIMESTAMP 时间分量）口径亦未定义。
- 登记记录"其他字段"（LIMIT_SUM_CONTENT、CLIENT_NO、PRE_REFERENCE、TRAN_CCY、REFERENCE、CREATE_TIMESTAMP、LAST_UPD_TIMESTAMP）自动生成的具体取值规则：需求明示按系统规则生成且未定义规则。
- 存量主键 (CHECK_OBJ_VAL, LIMIT_SCENE_NO) 重复导致的新增失败、事务边界与提交管理：属技术异常传播与工程框架职责，需求未定义。
- 已有累计记录的更新维护（如金额、笔数的累加更新）：需求正文仅含条件满足时的"登记"，更新路径不在本步骤范围。
- 登记结果在后续交易流程中的使用；限额检查判定本身（检查限额组件职责）。
- 本任务无组件内步骤调用补充说明，该约定为不适用。
